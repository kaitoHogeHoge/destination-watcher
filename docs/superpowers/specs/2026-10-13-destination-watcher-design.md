# 行き先ウォッチャー 設計書

作成日：2026-10-13

## 1. 目的

気になる旅行先（国・都市）をウォッチリストに登録しておくと、日々変わる情報を毎日自動で取得して画面に並べる。
それを見て「今どこに行くのが良さそうか」を比較・判断できるようにする。

### 成功の条件（最初のバージョン）

- ロンドン・トロムソ・シンガポールの3都市について、5種類の情報がカードで表示される
- データは GitHub Actions で毎日1回自動更新され、GitHub Pages の公開 URL から見られる
- どれか1つの情報の取得に失敗しても、他の情報は更新・表示される
- 各情報に「最終更新日時」が表示される
- スマホで見ても崩れない
- 費用は0円（サーバー・クラウドの契約なし）

## 2. 前提と決めたこと

| 項目 | 内容 |
|---|---|
| 置き場所 | `~/destination-watcher`（独立した Git リポジトリ） |
| GitHub リポジトリ | 公開（Public）。無料プランで GitHub Pages を使うため。ウォッチリストの内容も公開される |
| データ取得 | Python 3.12。外部ライブラリは `requests` のみ（テスト用に `pytest`） |
| 画面 | HTML / CSS / JavaScript。ビルド作業なし。グラフは Chart.js（CDN、版を固定） |
| 構成方針 | 「取得結果を JSON としてリポジトリに保存し、画面がそれを読む」方式 |

採用しなかった方式：
- Actions で HTML まで生成する方式：画面の修正に Python の修正が必要になるため
- ブラウザが直接 API を呼ぶ方式：過去の値が残らずグラフが作れない、外務省データをブラウザから直接取れない可能性があるため

## 3. フォルダ構成

```
destination-watcher/
├── config/
│   └── destinations.json        行き先リスト
├── fetcher/

│   └── sources/
```

| 項目 | 必須 | 意味 |
|---|---|---|
| `id` | ○ | 英小文字の識別名。保存ファイル名に使う |
| `name` / `country` | ○ | 画面に出す日本語名 |
| `country_code` | ○ | ISO 2文字の国コード（祝日で使う） |
| `holiday_region` | – | 地域限定の祝日を絞り込むときの地域コード（例：`GB-ENG`）。省略時は全国共通の祝日のみ |
| `mofa_code` | ○ | 外務省オープンデータの国番号（4桁、国際電話の国番号と同じ） |
| `lat` / `lon` | ○ | 緯度・経度（天気・気候で使う） |
| `currency` | ○ | ISO 3文字の通貨コード（為替で使う） |

## 5. 情報ごとの取得処理（sources）

### 5.1 共通の約束

各情報は次の形の「部品」として作る。

```python
class Source:
    name = "exchange"          # 識別名（保存ファイル名に使う）
    label = "為替レート"         # 画面の見出し
    refresh_days = 0           # 何日ごとに取り直すか（0 = 毎回）

    def fetch(self, dest, previous):
        """行き先1つ分の情報を取得して dict を返す。
        previous は前回保存した data（無ければ None）。
        失敗したら例外を投げる（司令塔が受け止める）。"""
```

- `sources/__init__.py` に部品の一覧を置き、`main.py` はその一覧を順に呼ぶだけにする
- 新しい情報を足すとき：`sources/新しい情報.py` を作り、一覧に1行足し、画面に表示部分を足す
- 通信はタイムアウト（20秒）を必ず付ける。失敗時は1回だけ再試行する

### 5.2 為替（exchange.py）

- API：Frankfurter `https://api.frankfurter.dev/v1/`（APIキー不要、欧州中央銀行の参考レート）
- 取得：`/v1/{開始日}..?base=JPY&symbols={通貨}`
- 表示用には「1外貨 = 何円」に換算する（API は「1円 = 何外貨」で返すため逆数を取る）
- 履歴：前回の履歴に、新しい日付の値を足して保存する
  - 初回（履歴が無いとき）は過去365日分をまとめて取得する
  - 2回目以降は「前回の最終日」以降だけ取得する
- 欧州中央銀行の営業日のみ値がある（土日・祝日は値が増えない）

### 5.3 天気予報（forecast.py）

- API：Open-Meteo `https://api.open-meteo.com/v1/forecast`
- 取得項目（日ごと）：最高気温、最低気温、天気コード、降水量、降水確率
- `forecast_days=16`、`timezone=auto`（現地の日付で返る）
- 天気コード（WMO コード）は画面側で日本語と絵文字に変換する（例：0 = ☀ 快晴）

### 5.4 月ごとの気候（climate.py）

- API：Open-Meteo 過去データ `https://archive-api.open-meteo.com/v1/archive`
- 直近10年分（前年までの10暦年）の日ごとの平均気温・降水量を取得し、月ごとに平均する
  - 気温：その月の日平均気温の平均
  - 降水量：その月の合計降水量の10年平均
- 結果は年に何度も変わらないため `refresh_days = 30`（30日に1回だけ取り直す）

### 5.5 祝日（holidays.py）

- API：Nager.Date `https://date.nager.at/api/v3/PublicHolidays/{年}/{国コード}`
- 今日から6か月先までの祝日を表示する（年をまたぐ場合は2年分取得して結合）
- 絞り込み：全国共通（`global: true`）の祝日と、`holiday_region` に該当する地域の祝日のみ
- 名前は `localName`（現地語）と `name`（英語）の両方を保存する

### 5.6 海外安全情報（safety.py）

- データ：外務省 海外安全情報オープンデータ（軽量版 XML）
  `https://www.ezairyu.mofa.go.jp/opendata/country/{mofa_code}L.xml`
- 読み取る項目：
  - `riskLevel1`〜`riskLevel4`（国内のどこかにそのレベルの地域があれば 1）→ 1 が立っている最大の数字を「危険レベル」とする（無ければ 0）
  - `infectionLevel1`〜`4` → 同様に「感染症危険レベル」
  - `riskTitle`（危険情報の見出し）、`lastModified`（外務省側の更新日時）
- 画面には外務省の該当ページへのリンクを付ける（出典表示を兼ねる）
- 変化の検出：前回の値と比べ、危険レベルまたは感染症危険レベルが変わっていたら
  `changed: true`、`changed_at`（変化を検出した日時）、`previous_level` を記録する
  - 「変化あり」の表示は、変化を検出してから7日間続ける

## 6. 保存するデータ

### 6.1 ファイルの置き場所

```
site/data/
├── index.json                  行き先の一覧と、全体の最終実行日時
└── {行き先id}/
    ├── exchange.json
    ├── forecast.json
    ├── climate.json
    ├── holidays.json
    └── safety.json
```

### 6.2 1ファイルの形

```json
{
  "source": "exchange",
  "status": "ok",
  "updated_at": "2026-10-13T06:00:00+09:00",
  "attempted_at": "2026-10-13T06:00:00+09:00",
  "error": null,
  "data": { }
}
```

| 項目 | 意味 |
|---|---|
| `status` | `ok`（成功）／`error`（今回失敗） |
| `updated_at` | 最後に**成功**した日時（画面の「最終更新」） |
| `attempted_at` | 最後に取得を**試みた**日時 |
| `error` | 失敗時の短い説明（日本語）。成功時は `null` |
| `data` | 情報ごとの中身 |

日時はすべて日本時間（+09:00）で記録する。

## 7. 失敗したときの扱い

- `main.py` は「行き先 × 情報」の組ごとに取得処理を `try` で囲む。1つ失敗しても次へ進む
- 失敗したときは、前回のファイルの `data` と `updated_at` を残したまま、`status: "error"`、`error`、`attempted_at` だけを書き換える
- 初めての取得で失敗した場合は `data: null` で保存する
- 設定ファイル自体が読めない・必須項目が欠けている行き先は、その行き先だけ飛ばしてログに残す
- 最後に結果の一覧（成功 n 件・失敗 m 件）をログに出す。失敗があっても処理全体は「成功」として終える（Actions が赤くならないことで、自動保存が止まらないようにする）
  - ただし**全部**失敗したときは異常終了にして、Actions の画面で気づけるようにする

## 8. 画面

- 上部：タイトルと全体の最終実行日時
- 行き先ごとのカードを並べる。画面幅に応じてスマホ1列／タブレット2列／パソコン3列
- カードの中は情報ごとの区切りに分ける。各区切りの右上に「最終更新：10/13 6:00」を出す
  - `status: "error"` のときは「⚠ 取得に失敗しました（10/12 6:00 時点のデータを表示中）」
  - `data` が無いときは「データがまだありません」
- 区切りごとの表示内容：
  - **為替**：現在値（1外貨 = ○円）、前日比、30日前比。推移の折れ線グラフ（30日／90日／1年を切り替え）
  - **天気予報**：16日分を横スクロールで表示（日付・天気の絵文字・最高／最低気温・降水確率）
  - **気候**：12か月の表（平均気温・降水量）。今月の列を目立たせる
  - **祝日**：今後6か月の祝日一覧（日付・曜日・名前）
  - **安全情報**：危険レベルを色付きの札で表示（0 = 情報なし、1〜4 は外務省の色に合わせる）。「変化あり」のときはカードの枠ごと強調し、「レベル1→2（10/13 検出）」と書く
- 画面の表示部分も情報ごとに関数を分け、新しい情報を足しやすくする
- 文字はすべて日本語。日付は「10/13（月）」の形

## 9. 自動実行（GitHub Actions）

- `.github/workflows/update.yml`
- 毎日1回実行：日本時間 6:00（世界標準時 21:00）を指定。混雑時は数十分遅れることがある
- 手動でも実行できるようにする（`workflow_dispatch`）
- 手順：Python を用意 → `requirements.txt` を入れる → `python -m fetcher.main` → `site/data/` に変更があればコミットして push
- 同時に2つ動かないようにする（`concurrency`）

## 10. 公開（GitHub Pages）

- `site/` フォルダを公開する（Actions の Pages 公開機能を使い、データ更新の後に公開まで行う）
- 公開 URL は `https://<GitHubユーザー名>.github.io/destination-watcher/`

## 11. テスト

- `tests/fixtures/` に各 API の実際の応答を保存し、通信なしで次を確かめる
  - 各 source が応答を正しく読み取れること（為替の逆数換算、気候の月平均、祝日の絞り込み、危険レベルの判定など）
  - 安全情報の変化検出（変化あり／なし／初回）
  - 1つの source が例外を出しても、他の source の保存が行われること
  - 失敗時に前回の `data` と `updated_at` が残ること
- 画面は手元のサーバー（`python -m http.server`）でブラウザ表示して確認する

## 12. 進め方

| ステップ | 内容 | 動作確認 |
|---|---|---|
| 1 | ロンドン × 為替のみ。取得 → 保存 → 画面表示まで | 取得コマンドの実行 → 手元のサーバーでブラウザ表示 |
| 2 | 残り4種類の情報と残り2都市を追加 | 全カードの表示確認。わざと1つ失敗させて他が出ることを確認 |
| 3 | GitHub に置き、Actions で毎日自動取得 | Actions タブで手動実行し、成功と JSON の更新を確認 |
| 4 | GitHub Pages で公開 | 公開 URL をスマホで開いて確認 |

各ステップの最初に、使う API の仕様を改めて確認する。各ステップの終わりに動作確認の方法を説明してから次へ進む。
